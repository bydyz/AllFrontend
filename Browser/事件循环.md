# 事件循环与浏览器渲染原理

## 一、进程与线程

### 1.1 什么是进程？

进程是程序运行时所需的**专属内存空间**。

**核心要点：**
- 程序（如QQ、微信、游戏）运行时需要内存来存储变量、对象、函数等
- 每个程序启动时至少有一个进程
- 进程之间相互独立，内存空间相互隔离

**隔离的好处：** 一个进程崩溃不会影响其他进程。进程之间如果需要通信，需要双方同意。

### 1.2 什么是线程？

有了进程（内存空间）后，需要有人来**运行代码**，这个"运行代码的人"就是线程。

**核心要点：**
- 一个进程至少得有一个线程，否则进程会被系统杀死
- 进程启动时自动创建的线程称为**主线程**
- 主线程结束后，整个程序就结束
- 复杂的程序可能需要多个线程（如游戏需要同时处理用户操作、网络通信等）
- 一个进程中的多个线程**共享同一块内存空间**

```javascript
// 线程共享内存空间的示例
const sharedData = { count: 0 };

// 线程A和线程B可以同时访问同一个变量
// 线程A: sharedData.count++  (读取0，自增后写入1)
// 线程B: sharedData.count++  (读取0，自增后写入1)
// 最终结果可能是1而不是2（竞态条件）
```

## 二、浏览器的进程模型

浏览器是一个**多进程、多线程**的应用程序，其复杂度已接近操作系统。

### 2.1 浏览器的主要进程

| 进程 | 职责 |
|------|------|
| **浏览器进程** | 界面展示、用户交互、子进程管理等 |
| **网络进程** | 网络资源的加载 |
| **渲染进程** | 每个标签页一个，负责页面渲染 |

> 💡 **注意：** 每个标签页都有一个独立的渲染进程，保证标签页之间互不影响。这也是 Chrome 被称为"内存杀手"的原因。未来可能会改为"一个站点一个进程"的模式。

```javascript
// 浏览器进程架构示意
// Browser Process (主进程)
//   ├── Renderer Process (标签页1)
//   │     └── Main Thread (主线程)
//   ├── Renderer Process (标签页2)
//   │     └── Main Thread (主线程)
//   └── Network Process (网络进程)
```

## 三、渲染主线程

渲染进程启动后，会开启一个**渲染主线程**。

### 3.1 渲染主线程要做的事情

| 任务 | 说明 |
|------|------|
| 解析 HTML、CSS、JS | 将代码转换为可执行的指令 |
| 计算样式 | 将 em、百分比等转换为 px |
| 布局 | 计算每个元素的几何信息（宽高、位置） |
| 图层处理 | z-index 控制图层前后 |
| 绘制 | 每秒绘制页面 60 次（帧率 FPS） |
| 执行 JS 代码 | 全局代码、事件处理函数、计时器回调 |

### 3.2 为什么不多开几个线程？

**结论：没有办法，它只能这样干。**

主要原因：**任务调度问题**。比如：

```javascript
// 场景1：执行JS到一半时，用户点击了按钮，怎么办？
element.addEventListener('click', () => {
  // 这个回调何时执行？
});

// 场景2：执行JS到一半时，计时器到时间了，怎么办？
setTimeout(() => {
  // 这个回调何时执行？
}, 1000);

// 场景3：用户点击和计时器同时到达，先处理哪一个？
```

**解决方案：排队！** 这就是事件循环的核心思想。

## 四、事件循环（Event Loop）

### 4.1 核心机制

渲染主线程有一个**消息队列**（Message Queue），也叫事件队列。

```
┌─────────────────────────────────────────────────────────┐
│                    渲染主线程                            │
│  ┌───────────┐     ┌───────────┐     ┌───────────┐    │
│  │  任务 A   │ ──▶ │  任务 B   │ ──▶ │  任务 C   │    │
│  └───────────┘     └───────────┘     └───────────┘    │
│                                                         │
│  主线程永远在循环：从队列中取任务 → 执行 → 取下一个      │
└─────────────────────────────────────────────────────────┘
                        ▲
                        │ 其他线程往队列中添加任务
                        │
    ┌───────────────────┼───────────────────────────────┐
    │                   │                               │
    ▼                   ▼                               ▼
┌─────────┐     ┌─────────┐                    ┌─────────┐
│交互线程  │     │计时线程  │                    │网络线程  │
│点击事件  │     │setTimeout│                    │请求完成  │
└─────────┘     └─────────┘                    └─────────┘
```

### 4.2 工作流程

```javascript
// 事件循环伪代码
function eventLoop() {
  while (true) {
    // 1. 检查消息队列是否有任务
    if (messageQueue.isEmpty()) {
      // 2. 如果没有任务，主线程休眠
      sleep();
    } else {
      // 3. 如果有任务，取出第一个任务执行
      const task = messageQueue.dequeue();
      execute(task);
    }
  }
}
```

**执行流程：**
1. 渲染主线程进入无限循环
2. 每次循环检查消息队列中是否有任务
3. 如果有 → 取出第一个任务执行
4. 如果没有 → 进入休眠状态
5. 其他线程随时可以向队列末尾添加任务
6. 如果主线程处于休眠状态，有任务到来时会被唤醒

### 4.3 事件循环的本质

**事件循环（Event Loop）**，也叫消息循环（Message Loop），是渲染主线程的工作方式。

它开启一个永不结束的 `for` 循环，每次循环从消息队列中取出一个任务执行，这就是一次**事件循环**。

```javascript
// 事件循环的本质 - 伪代码
for (;;) {
  const task = getNextTask();  // 从队列取任务
  if (task) {
    task.execute();            // 执行任务
  }
}
```

## 五、异步

### 5.1 为什么需要异步？

有些任务无法立即执行，比如：

- `setTimeout`（需要等待指定时间）
- 网络请求（需要等待服务器响应）
- 事件监听（需要等待用户操作）

如果让渲染主线程傻等这些任务完成，就会导致：

- 主线程被阻塞
- 页面无法及时绘制（每秒 60 次无法保证）
- 用户感知到卡顿甚至卡死

### 5.2 异步的实现方式

以 `setTimeout` 为例：

```javascript
// 异步执行流程
console.log('1. 开始');

setTimeout(() => {
  console.log('4. setTimeout 回调执行');
}, 2000);

console.log('2. 继续执行');

// 输出：
// 1. 开始
// 2. 继续执行
// (2秒后)
// 4. setTimeout 回调执行
```

**执行流程解析：**

```javascript
// 1. 主线程执行到 setTimeout
setTimeout(() => { ... }, 2000);

// 2. 主线程通知计时线程开始计时，立即继续执行后续代码
console.log('2. 继续执行');

// 3. 计时线程计时结束后，将回调函数包装成任务放入消息队列

// 4. 等待主线程空闲时从队列中取出执行
```

### 5.3 核心理解

> **单线程是异步产生的原因，事件循环是异步的实现方式。**

```javascript
// JS 是单线程语言（运行在渲染主线程上）
// 使用同步方式会导致主线程阻塞

// 同步方式（阻塞）- 不推荐
function synchronousRequest() {
  const xhr = new XMLHttpRequest();
  xhr.open('GET', '/api/data', false);  // false = 同步
  xhr.send();
  // 主线程在这里等待服务器响应，页面卡死
  return xhr.responseText;
}

// 异步方式（非阻塞）- 推荐
function asynchronousRequest() {
  const xhr = new XMLHttpRequest();
  xhr.open('GET', '/api/data', true);  // true = 异步
  xhr.onload = function() {
    // 主线程不会等待，请求完成后才执行这个回调
    console.log(xhr.responseText);
  };
  xhr.send();
  // 主线程立即继续执行后续代码
}
```

## 六、任务队列的优先级

过去简单地将任务分为宏任务和微任务两个队列，但现已无法满足复杂场景。

### 6.1 W3C 最新规定

- 同一个类型的任务必须在同一个队列
- 不同类型的任务可以分属不同队列
- 浏览器必须有一个**微队列**（Micro Queue）
- 微队列中的任务**优先级最高**，必须优先执行

### 6.2 Chrome 浏览器中的队列（至少包含）

| 队列 | 存放内容 | 优先级 |
|------|----------|--------|
| **微队列** | Promise、MutationObserver 等 | 最高 |
| **交互队列** | 用户点击、滚动、键盘事件等 | 高 |
| **延时队列** | setTimeout、setInterval 回调 | 适中 |

> 💡 **注意：** 在一次事件循环中，由浏览器自行决定从哪个队列取任务，但微队列必须优先执行。

### 6.3 加入微队列的方式

```javascript
// 方式1：使用 Promise
Promise.resolve().then(() => {
  console.log('这是微任务');
});

// 方式2：使用 queueMicrotask（推荐，语义更清晰）
queueMicrotask(() => {
  console.log('这也是微任务');
});

// 方式3：MutationObserver（DOM变化观察）
const observer = new MutationObserver(() => {
  console.log('DOM变化，这也是微任务');
});
observer.observe(document.body, { childList: true });
```

## 七、为什么 JS 会阻碍渲染？

看下面这段代码：

```javascript
const h1 = document.querySelector('h1');
const btn = document.querySelector('button');

// 死循环指定时间
function delay(duration) {
  const start = Date.now();
  while (Date.now() - start < duration) {}
}

btn.onclick = function() {
  h1.textContent = '袁老师很帅';  // 修改文本
  delay(3000); // 死循环3秒
};
```

### 点击按钮后会发生什么？

1. 文本修改后不会立即显示
2. 页面会卡住 3 秒
3. 3 秒后才显示出修改后的文本

### 原因分析

```javascript
// 1. 修改文本后会产生一个绘制任务，被放入消息队列
// 2. delay(3000) 在主线程上执行了 3 秒的循环
// 3. 主线程在这 3 秒内无法处理绘制任务
// 4. 3 秒后主线程空闲，才从队列中取出绘制任务执行
```

> **结论：JS 和渲染都在同一个渲染主线程上，一方执行时另一方必须等待。**

## 八、面试题示例

### 8.1 基础题

```javascript
setTimeout(() => {
  console.log(1);
}, 0);
console.log(2);

// 输出：2 1
```

**原因：** 虽然计时器是 0 秒，但回调函数要等全局代码执行完毕后才会被取出执行。

### 8.2 微任务与延时任务混合

```javascript
setTimeout(() => {
  console.log(1);
}, 0);

Promise.resolve().then(() => {
  console.log(2);
});

console.log(3);

// 输出：3 2 1
```

**原因：** 微队列优先级高于延时队列。

### 8.3 嵌套计时器

```javascript
setTimeout(() => {
  console.log(1);
  setTimeout(() => {
    console.log(2);
    setTimeout(() => {
      console.log(3);
    }, 0);
  }, 0);
}, 0);
console.log(4);

// 输出：4 1 2 3
```

### 8.4 复杂嵌套

```javascript
setTimeout(() => {
  console.log(1);
  Promise.resolve().then(() => {
    console.log(2);
  });
}, 0);

Promise.resolve().then(() => {
  console.log(3);
});

console.log(4);

// 输出：4 3 1 2
```

## 九、计时器能做到精确计时吗？

**答案：不能。** 原因有四个：

| 层面 | 原因 |
|------|------|
| **硬件限制** | 计算机没有原子钟，无法做到绝对精确 |
| **操作系统偏差** | 计时器最终调用操作系统的 API，不同系统实现不同，本身就有偏差 |
| **嵌套层级限制** | 按照 W3C 标准，计时器嵌套层级超过 5 层时，最少间隔时间为 4ms |
| **事件循环影响** | 计时器的回调函数只能在主线程空闲时执行，即使计时已到期，也得排队等待 |

```javascript
// 嵌套超过5层后，0ms 会变成至少 4ms
setTimeout(() => {
  setTimeout(() => {
    setTimeout(() => {
      setTimeout(() => {
        setTimeout(() => {
          setTimeout(() => {
            // 这一层开始，最小间隔为 4ms
          }, 0);
        }, 0);
      }, 0);
    }, 0);
  }, 0);
}, 0);
```

## 十、总结

### 核心概念回顾

| 概念 | 说明 |
|------|------|
| **进程** | 程序运行时分配的内存空间，相互隔离 |
| **线程** | 运行代码的基本单元，一个进程至少一个线程 |
| **渲染主线程** | 浏览器渲染进程中的主线程，负责解析、布局、绘制、执行 JS 等 |
| **事件循环** | 主线程不断从消息队列中取任务执行的无限循环机制 |
| **消息队列** | 存放待执行任务的队列，可以有多个 |
| **微队列** | 优先级最高的队列，任务必须优先执行 |
| **异步** | 通过事件循环实现的非阻塞执行模式 |

### 两道关键表述

#### 阐述 JS 的事件循环：

1. 事件循环是渲染主线程的工作方式
2. 主线程开启永不结束的 `for` 循环
3. 每次循环从消息队列取一个任务执行
4. 其他线程在合适的时机把任务加到队列末尾
5. 任务有多个队列，微队列优先级最高

#### JS 中的计时器能否精确计时？

**不能**，原因：
1. 硬件层面：无原子钟
2. 操作系统层面：API 本身有偏差
3. 浏览器层面：嵌套超过 5 层最小间隔 4ms
4. 事件循环层面：回调必须等待主线程空闲

### 最后一句经典总结

> **单线程是异步产生的原因，事件循环是异步的实现方式。**
