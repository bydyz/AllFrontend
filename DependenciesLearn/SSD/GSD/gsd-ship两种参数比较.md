# `/gsd-ship` 两种参数比较

当你在 GSD 工作流中准备好成果，准备对外发布时，会用到 `/gsd-ship` 这个命令。你的问题提得很细，`/gsd-ship <阶段编号>` 和 `/gsd-ship milestone` 这两个命令目标不同，前者是为了将某个具体功能的代码交付出去，后者则是为了对外发布一个完整的版本，并为下一个版本周期做准备。

---

## 1. `/gsd-ship <阶段编号>`：交付单个功能

它的核心作用，是将某个 **Phase（阶段）** 下已验证成功的工作成果，从开发环境正式交付出去。

在 GSD 的工作流中，一个标准的 Phase 在开发完成后，必须经过 `/gsd-verify-work` 命令的严格验证，确认它确实满足了需求。之后，就会用 `/gsd-ship` 把它变成可交付的代码。执行后，该阶段的产出通常会生成一个**合并请求（Pull Request）**，等待最终合入主分支。

**下一步通常会是：**

1. 处理代码审查（Code Review）。
2. 合并 PR。
3. 接着，你就可以开启项目路线图中的下一个 Phase 了。

---

## 2. `/gsd-ship milestone`：发布完整版本

这个命令的含义与上文的"交付代码"有所不同。它的核心作用是对外发布一个**完整的"里程碑版本"**，并将这个版本标记为存档。

一个 **Milestone（里程碑）** 由多个 Phase 组成，代表一次完整的版本发布。当你完成了某个里程碑下的所有 Phase，并确认一切就绪后，就应该使用这个命令。它会打包这整个版本的成果，并为这个版本打上 **Git 标签（Tag）**，表示一个正式版本的诞生。

**下一步通常会是：**

1. **开始新的开发周期。** 你可以使用 `/gsd-new-milestone` 命令，正式创建下一个里程碑，开启新一轮的"讨论、规划、执行、验证"循环。
2. **对整个里程碑进行审计（可选）。** 使用 `/gsd-audit-milestone` 来回顾整个周期，总结经验。

---

## 总结对比：两大命令的区别

为了让你更清晰地看到它们的区别，我把核心信息整理成了一张表：

| 命令 | 核心本质 | 执行后的主要产出 | 下一步通常做什么 |
|------|---------|----------------|----------------|
| `/gsd-ship <阶段编号>` | 交付单个功能，完成一次内部迭代 | - 创建该功能的 PR<br>- 准备代码审查与合并 | - 处理代码审查<br>- 合并 PR<br>- 启动项目路线图中的下一个 Phase |
| `/gsd-ship milestone` | 发布完整版本，完成一个开发周期 | - 打包整个里程碑<br>- 在 Git 上打版本标签 | - 开启新的里程碑（`/gsd-new-milestone`）<br>-（可选）审计当前里程碑（`/gsd-audit-milestone`） |

---

## 💎 一个完整的里程碑推进示例

你可以看看这个例子，能帮你更好地理解整个过程：

1. 你完成了 **Milestone 1**（里程碑 1）的第一个 Phase。
2. 你运行 `/gsd-ship 1`，创建 PR。
3. 其他 Phase 完成后，也依次执行 `/gsd-ship 2`、`/gsd-ship 3`。
4. 当 Milestone 1 的所有 Phase 都"ship"并通过审查合入主分支后，你运行 `/gsd-ship milestone`，它会在 Git 仓库里打上一个正式的版本标签，比如 `v1.0.0`。

---

从它们的职责看，这两个命令不能混用。`/gsd-ship milestone` 是多个 phase 完成后，一次"盛大"的总结和发布。想继续了解 `/gsd-audit-milestone` 如何进行里程碑审计吗？或者我们可以聊聊如何规划你的第一个里程碑。
