# gsd-verify-work 命令详解

## 基本信息

| 属性 | 值 |
|------|-----|
| 命令名称 | `/gsd-verify-work` |
| 功能描述 | 通过对话式 UAT 验证已构建的功能 |
| 参数提示 | `[phase number, e.g., '4'] [--ws <name>]` |

## 功能概述

通过对话式测试验证已构建的功能，持续状态。

**目的**：确认 Claude 构建的内容实际上从用户的角度来看是有效的。一次一个测试，纯文本响应，不 interrogation。发现问题时会自动诊断、计划修复，并准备好执行。

**输出**：跟踪所有测试结果的 `{phase_num}-UAT.md`。如果发现问题：已诊断的差距，已验证的修复计划准备好用于 `/gsd-execute-phase`

## 参数详解

| 参数 | 说明 |
|------|------|
| `phase number` | 可选。要测试的具体阶段号（如 "4"） |
| `--ws <name>` | 可选。使用特定的 workspace |

## 执行流程详解

### 第一步：会话管理

```
1. 确定测试的阶段
2. 如果提供了阶段号，直接使用该阶段
3. 如果未提供，检查是否有活动会话
4. 如有活动会话，恢复它
5. 如没有活动会话，创建新会话
```

### 第二步：加载上下文

```
6. 读取相关文件：
   - PROJECT.md
   - REQUIREMENTS.md
   - 本阶段的 PLAN.md
   - 之前生成的 UAT.md（如果有）
```

### 第三步：生成测试用例

```
7. 从验收标准生成测试用例
8. 整理成对话式测试
9. 测试按功能分组
10. 每个测试独立展示
```

测试生成原则：

- 每个测试对应一个验收标准
- 测试要具体、可操作
- 避免 yes/no 问题，要求实际响应
- 一次展示一个测试，让用户逐步验证

### 第四步：执行测试

```
11. 展示第一个测试给用户
12. 用户回复响应（通过/失败/跳过）
13. 如果通过，继续下一个测试
14. 如果失败，进入诊断模式
15. 如果跳过，记录并继续
```

### 第五步：诊断问题（如有问题）

```
16. 分析失败的原因
17. 探索代码找出问题根源
18. 制定修复计划
19. 生成 gap-closure 任务列表
20. 自动准备好执行
```

诊断过程：

```
用户: 测试 X 失败了，显示错误 Y

诊断流程：
1. 分析错误信息
2. 定位相关代码
3. 识别根本原因
4. 评估修复复杂度
5. 生成修复计划
```

### 第六步：生成修复计划（如有问题）

```
21. 为每个问题创建修复任务
22. 标记为 gap_closure: true
23. 准备好执行
```

### 第七步：生成 UAT 报告

```
24. 汇总所有测试结果
25. 记录问题和解决方案
26. 生成 {phase_num}-UAT.md
```

## UAT 报告结构

```markdown
# Phase {N} UAT Report

## 会话信息
- 日期: {date}
- 时长: {duration}

## 测试结果

### 功能 模块 A
✅ 测试 1: 描述
✅ 测试 2: 描述
❌ 测试 3: 描述
   原因: {reason}
   修复: Task created

### 功能 模块 B
✅ 测试 4: 描述

## 问题汇总
| # | 测试 | 状态 | 原因 | 修复 |
|---|------|------|------|------|
| 1 | Test 3 | 未通过 | 原因1 | 已创建任务 |

## 后续步骤
- [ ] 运行 /gsd-execute-phase 以修复发现的问题
- [ ] 修复后重新运行 /gsd-verify-work
```

## 成功标准

- [ ] 所有验收标准都经过测试
- [ ] 测试结果已记录
- [ ] 发现的问题已诊断
- [ ] 修复计划已准备好
- [ ] 用户确认功能正常

## 测试策略

### 功能优先

```
测试顺序：
1. 核心功能（Must Have）
2. 重要功能（Should Have）
3. 增强功能（Nice to Have）
```

### 对话式而非审问式

```
❌ 问：这符合你的预期吗？（Yes/No）
✅ 尝试保存一个复杂文档，告诉我发生了什么
```

### 每次一个测试

```
一次展示一个测试：
"让我测试 X 功能。请尝试 Y，告诉我 Z。"

而不是：
"以下是要测试的 20 件事..."
```

### 具体错误信息

```
当测试失败时：
1. 要求具体的错误信息
2. 不是"出错了"而是具体的错误信息
3. 必要时提供重现步骤
```

## 问题分类

### 可快速修复

```
问题类型：简单配置错误
修复：直接给出修复建议，用户选择是否立即修复
```

### 需要重新执行

```
问题类型：需要改动代码
修复：创建 gap-closure 任务，用户选择是否执行
```

### 设计问题

```
问题类型：需要重新设计某部分
修复：建议回到 discuss-phase 重新讨论
```

## 差距关闭

当 verify-work 发现问题时：

```
Gap closure 流程：
1. verify-work 识别问题
2. 创建 gap-closure 任务
3. 运行 /gsd-execute-phase --gaps-only
4. 执行差距关闭任务
5. 重新运行 verify-work
```

## 后续步骤

在 `/gsd-verify-work` 完成后：

1. **如果通过**：运行 `/gsd-ship {N}` 创建 PR
2. **如果有问题**：运行 `/gsd-execute-phase --gaps-only` 修复问题，或者运行 `/gsd-execute-phase` 从头重新执行该阶段

## 与其他命令的关系

| 命令 | 关系 |
|------|------|
| `/gsd-execute-phase` | verify-work 的前置命令，执行计划 |
| `/gsd-ship` | verify-work 通过后的下一步，创建 PR |
| `/gsd-progress` | 检查进度，可能建议运行 verify-work |

## Workspace 支持

使用 `--ws <name>` 指定 workspace：

```
验证在特定 workspace 中进行
适用于：
- 多分支同时验证
- 并行工作流
```
